# Internationalization Guidelines

## Goal

Nexa ships to users across all supported locales. Internationalization is not a cleanup step; it is a product requirement.

## Supported Locales

Current shipped locales:

- `en`
- `zh-CN`
- `zh-TW`
- `ja`
- `ko`
- `fr`
- `de`
- `es`
- `pt`
- `ru`

## Non-negotiable Rules

### 1. No user-facing hardcoded strings in components

All user-visible UI copy must go through i18n keys.

This includes:

- labels
- helper text
- headings
- button text
- badges
- status text
- empty states
- hints

### 2. New UI copy requires all locale entries

Translations are authored in namespace JSON files under
`apps/desktop/src/i18n/locales/<locale>/<namespace>.json`. English is the base
locale. Each namespace contains string values, and callers use
`t('namespace.key')`.

When adding a translation key:

1. Add it to the appropriate English namespace JSON.
2. Add the matching key to the same namespace in every shipped locale.
3. From `apps/desktop`, run `npm run i18n:generate` and then
   `npm run i18n:check`.
4. Use the generated key in the component and verify the affected layouts.

`types.ts` and each locale's `index.ts` are generated by
[i18n-namespaces.mjs](../apps/desktop/scripts/i18n-namespaces.mjs). Edit the JSON
source instead of these generated files. The generator validates locale parity
before writing; a missing translation must be fixed before generation can pass.

Do not leave partial locale coverage for later.

### 3. Prefer reusable semantic keys

Good:

- `chat.investigationStatusReady`
- `chat.investigationEvidenceHigh`
- `search.scopeHint`

Bad:

- `chat.newHeaderThing`
- `misc.label7`
- page-specific keys for concepts already used elsewhere

### 4. Avoid engineer-only wording

Translations should describe the product in ordinary language. Favor concepts users understand over internal architecture terms.

### 5. Keep interpolation simple

Prefer:

- `{count} cited sources`
- `{selected} of {total} sources selected`

Avoid long sentences with many placeholders unless necessary.

## Review Checklist

Before merging UI work:

- search for new hardcoded strings in changed components
- verify namespace/key parity and generated output with `npm run i18n:check`
- include each locale's namespace JSON changes and any generated output
- check that fallback English has not leaked into non-English locales for the changed area
- verify layouts still work with longer translated text

## Engineering Note

`npm test` and `npm run build` run the i18n check. Structural parity does not
establish translation quality: review meaning, interpolation, longer text,
keyboard navigation, phone layouts, and mixed CJK/Latin typography in the UI.

## Documentation language

Public engineering docs use English. The Chinese README remains an intentional
translation of the English entry point, including capability and platform
limitations. This policy does not change the ten supported UI locales or
require translating historical release entries and domain-specific examples.

See [Contributing](../CONTRIBUTING.md#documentation-and-translations) for
documentation checks and the publication boundary.
